# API

## Structure

- Root API router: `backend/routes/Api.js`
- Feature routes: `backend/routes/*.js`
- HTTP adapters: `backend/controllers/`
- Business workflows: `backend/services/`
- Persistence: `backend/repositories/`
- External/shared infrastructure: `backend/lib/`

## Adding an endpoint

1. Add or reuse repository operations.
2. Implement validation and workflow in a service.
3. Add a thin controller that maps request data and errors to HTTP responses.
4. Register middleware and route under the appropriate feature router.
5. Mount new feature routers in `routes/Api.js` if necessary.
6. Add frontend API access through the existing Axios setup in `frontend/src/lib/api.ts` or the feature's established client.

## Contract guidelines

- Use consistent JSON envelopes within the feature and meaningful HTTP status codes.
- `400`: malformed/invalid input; `401`: unauthenticated; `403`: unauthorized; `404`: absent resource; `409`: state/idempotency conflict; `422`: semantically invalid when established; `500/502`: internal/provider failure.
- Do not pass raw provider errors, SQL errors, or stack traces to clients.
- Normalize dates as ISO 8601 strings and keep status values explicit.
- Pagination responses should include items and sufficient paging metadata.
- Search, status, and date filters must be validated and parameterized.

## Project trash

- `GET /api/projects` lists active accessible projects; `?scope=trash` lists only the viewer's owned, recoverable projects, including `trashedAt` and `expiresAt`.
- `DELETE /api/projects/:id` moves an owned project to Trash. `POST /api/projects/:id/restore` restores it within 30 days. `DELETE /api/projects/:id?permanent=true` permanently marks an already-trashed project deleted. Ownership, frozen status, and state transitions are checked under a row lock. Uploads remain in the user's library.
- The main site asks for confirmation before Delete forever. Trashed projects cannot be opened or renamed; editor membership checks exclude trash. After a committed change, an authenticated internal access refresh closes revoked editor sockets; periodic access rechecks remain the fallback. The existing ten-minute cleanup schedule expires project trash.

## Video upload policy

- Editor `GET /api/media-assets/:id/usage` requires ownership of a trashed upload and reconstructs saved/live project and scene documents to list affected locations. Names of projects the uploader no longer belongs to are redacted. Delete forever opens a confirmation dialog and disables confirmation until this check succeeds.
- Editor `POST /api/media-assets/status` requires current project membership and accepts up to 100 source URLs. It reports permanently deleted original uploads, excluding recoverable trash. The editor refreshes on deletion, focus and every ten seconds, showing missing-media placeholders without changing clip timing or saved history. Export submission rejects visible permanently deleted uploads with 422. Delete forever and trash expiry directly delete unshared S3 objects before marking the media record deleted; database metadata remains. No storage-cleanup columns, migration or separate worker are required.

- Main site `GET /api/files/video-upload-policy` reads `video_upload_resolution` and returns the signed-in uploader's effective plan, upload resolution bounds, display label and next eligible upgrade. Editor `GET /api/uploads/policy` keeps `maxHeight`/`maxWidth` and `planOptions` for export limits and adds separate `maxUploadHeight`/`maxUploadWidth`; its notice label and next-plan fields describe upload quality. Responses are private/no-store. Editor also returns the main site's upgrade URL. Asset-library finalization and editor file/URL finalization enforce the current upload feature server-side, preserving aspect ratio and never upscaling smaller videos.
- New market video originals and editor file/URL video uploads enforce Free 720p, Premium 1080p, Business 2160p during server-side normalization. Bounds rotate for portrait; smaller videos are not upscaled. Business notices are hidden; image originals are unaffected.
- Editor presign/finalize/URL-import endpoints verify the signed editor session matches the upload owner. Finalize/import also require editable project membership. The cap is queried at finalization, never supplied by the client.
- Editor upload controls read `personal_upload_storage` from the effective plan's `plan_features` rows, including queued and selected transfers in capacity checks. Values such as `5GB`, `100GB`, and `1TB` use binary units. Presign/import reject uploads exceeding capacity; finalization re-reads the limit and checks actual stored size under a per-owner transaction lock. Only distinct original files belonging to non-deleted media assets count; trashed uploads still count until permanently deleted. Proxies, thumbnails, and project documents are excluded. The storage meter formats the actual allowance rather than assuming a tier's size.

## Editor collaborative project limits

- The `projects` plan feature caps the number of owned projects with another active member, rather than project creation or member count. `Unlimited` removes the cap. The project owner's plan applies even when a Manager shares it. Retained shared projects in Trash still count until permanently deleted or unshared; projects joined under somebody else's ownership do not consume a slot.
- Editor member-list responses include collaboration usage and whether this project can be shared for Owners/Managers. At the cap, an unshared project's Share modal hides adding people and copying links, keeps the access list visible, and offers an upgrade link to `/credits-subscriptions`. Existing collaborative projects remain shareable; membership management and publishing a template are separate from consuming a new collaborative-project slot.
- Direct member additions and share-link redemption check the cap inside the membership transaction, serialized by project and owner locks. Removing the last collaborator releases a slot under the same locks. Link creation checks capacity but does not reserve a slot; previously issued links are checked again when redeemed. Limit failures on add/link creation return 409 with `COLLABORATIVE_PROJECT_LIMIT`; invalid plan configuration fails closed. No migration is needed.


## Editor workspace panel

- Editor `GET /api/projects/:id/workspace` verifies the signed editor session, active project membership, and linked workspace access. It resolves project links across the workspace junction, primary project, job and gig references, and returns only the viewer's current contract milestones and explicitly assigned tasks. Contractual workspaces group their member contracts under the same team; regular team workspaces keep their member/manager boundary.
- Milestones are selected per contract, respecting direct freelancer, assigned subcontractor milestone, or contributing team membership. The editor task list includes the viewer's assigned tasks in their current milestones. Milestone progress counts the linked milestone tasks; personal progress counts all assigned tasks, deduplicated by task ID. Finished tasks determine the percentage; empty totals display 0%. Past-due unfinished tasks outside review count as overdue.
- Workspace reads require Owner, Manager or Editor project access and use existing tables with private/no-store responses. `PATCH` on the same endpoint accepts a task ID and status/priority changes, rechecks assignment and access, then delegates through the internal-secret-protected main API to the existing workspace mutation services. The Workspace right panel refreshes on open, focus, reconnect and every 30 seconds while visible. No new migration or dependency is required.

## External providers

- Editor caption submission resolves trusted marketplace proxy URLs through `media_assets.proxy_file_id` to `original_file_id` for active, published audio/video assets. Only the transcription provider receives an expiring S3 URL for the clean original; editor playback, caption source associations and export licensing are unchanged. This caption-only lookup also works for unlicensed previews. Unavailable clean sources return 422, and provider error details are withheld because they can contain signed URLs. Existing session and paid-plan checks still apply; other source URLs retain their normal transcription path.

- Set authentication and idempotency headers server-side.
- Configure timeouts and distinguish provider rejection from temporary transport failure.
- Store the provider reference required for webhook and reconciliation matching.
- Provider callbacks must be publicly reachable HTTPS endpoints in production.

## Realtime API

- Use Socket.IO for timely notification/presence/status updates, not as the sole source of truth.
- Event names and payload shapes must remain stable and scoped to authorized rooms/users.
- Always expose a normal HTTP read endpoint so refresh or reconnect restores current state.

## Badge catalog

- `GET /api/admin/badge-requirement-types` lists evaluable metrics (jobs, gigs, assets, profile, reviews, followers) plus honorary `admin_grant`.
- Catalog `POST/PATCH /api/admin/badges` stores one unlock on the badge: `{ triggerEventCode, conditionValue, badgeCategoryId }`. `category` (name) is still accepted if it matches a live row. `admin_grant` means honorary. Evaluation pending-grants when that one unlock is met.
- `GET /api/admin/badge-categories` lists live categories. `POST /api/admin/badge-categories` creates one (`{ name, description }`). Duplicate live names return 409.
- Badge payloads (`GET /api/admin/badges`, profile `badges`, discovery cards, `GET /api/accounts/badges/mine`) include `badge_category_id` and `category` (the live category name). The badges row stores only the foreign key.

## Platform Merit

- Not stored. Profile `standing.merit` and `GET /api/users/me/standing` `merit` are `clamp(100 − active warning points, 0, 100)`.
- Staff restriction payloads still include `warningPoints`. User-facing payloads should use `merit`.

## Account standing, credit holds, deactivation

- `GET /api/users/me` `restriction` (from `getAccountAccess`) adds `banEndsAt`, `lockEndsAt`, `warningBandLabel`, `warningBandEndsAt` (when the strictest running automatic band's fixed clock ends), `muted`, `mutedUntil`, `meritPenalties` (every automatic punishment running, strictest first), `creditsFrozen`, `frozenCredits`, `creditsFrozenAt`, `creditsFrozenUntil`, `creditsFrozenReason`, and `returnsToDeactivated`. Frozen access now carries its own `message`.
- `POST /api/admin/accounts/:accountId/credits/freeze` body `{ freeze, reason, days? | endsAt? }`. `reason` (≥ 5 chars, shown to the member) is required to freeze; `days` 1–365 or `endsAt` within 365 days sets the release date, neither means until staff review. Refuses your own account and (unless Admin) staff accounts. 409 when nothing is available to hold or release.
- Socket `account:credits_hold` `{ held, message, restriction }` follows a hold or release; the client refreshes its standing and wallet.
- `POST /api/admin/accounts/:accountId/credits/adjust` body `{ amount, note }` (signed whole number, ≤ 1,000,000; `note` ≥ 5 chars, shown to the member). Deductions only touch spendable credits (409 when short). The ledger row stays a self-transfer; a `CREDITS_ADJUSTED` account_activity row (metadata `delta`, `reason`, `balanceBefore/After`, `creditTransactionId`) is written in the same transaction, then the member gets a notification and socket `account:credits_adjusted`. Ticket credit changes use the same path.
- Credits & Economy desk (Admin and Support Moderator; Support never sees staff wallets or ledger rows touching one — 404 on a staff wallet): `GET /api/admin/economy-overview` (supply, 30-day flow + daily series, in-flight credits, leaders, recent adjustments/ledger, `alerts[]` with `action: { tab, filters }`, `viewer` capabilities); `GET /api/admin/economy/wallets` (`search`, `accountType`, `hold` = held|not_held|overdue|expiring|indefinite, `balance`, `accountStatus`, `sort`, `limit` ≤ 200, `offset`); `GET /api/admin/economy/wallets/:walletId` (wallet, hold, insights incl. ledger check, adjustments); `GET /api/admin/economy/ledger` (`search`, `kind`, `type`, `status`, `direction` with `walletId`, `accountId`, `from`/`to` dates, `minAmount`/`maxAmount`, `sort`, `limit` ≤ 100, `offset`). Paged responses are `{ items, total, limit, offset }`.
- `GET /api/accounts/deactivation` returns `deactivationAvailableAt`, `deactivationReady`, `canDeactivate`, `standingBlocksDeactivation`, `blockers { liveContracts, openDisputes }`, `cooldownHours`, `redeactivateCooldownDays`. `POST /api/accounts/deactivate` returns 409 with `code` `DEACTIVATION_COOLDOWN`, `DEACTIVATION_BLOCKED` or `DEACTIVATION_STANDING`. Both deactivate and reactivate write `ACCOUNT_DEACTIVATED` / `ACCOUNT_REACTIVATED` activity.
- Proposals, gig orders, job offers, new DMs and follows aimed at a deactivated member return 409 (`ACCOUNT_DEACTIVATED`) or the profile 404, before any credits move.
- `POST /api/accounts/dev/add-credits` and `/dev/add-rating` return 404 when `NODE_ENV=production`.

## Warning library

- `GET /api/admin/warning-catalog?desk=` lists live named warnings for a desk (admin/support see all). Same payload on `GET /api/moderator/warning-catalog` for restriction-desk staff. Each row includes locked `points` and `durationDays`.
- Admin CRUD: `GET/POST /api/admin/warning-defs`, `PATCH/DELETE /api/admin/warning-defs/:warningDefId`. Body `{ label, category, points, durationDays, desks, note }`. Points 1–10. Duration 1–365 days. Delete is a soft-delete. Staff-issued warnings copy points and duration; client-sent clocks are ignored.
- Admin-only punishment ladder: `GET/POST /api/admin/warning-thresholds`, `PATCH/DELETE /api/admin/warning-thresholds/:thresholdId`. Body `{ minPoints | triggerMerit, effect, label, durationDays, note }`. Effects: `limited`, `restricted`, `frozen`, `mute`, `auto_suspend`; `durationDays` 1–365 is required. See [warning-system.md](warning-system.md) §8.
- Automatic punishments: `GET /api/admin/accounts/:accountId/merit-penalties` (`{ ready, active, history }`), `POST /api/admin/accounts/:accountId/merit-penalties/end` `{ reason, penaltyIds?, effects? }` (Unfreeze, Admin / Support), `POST /api/admin/accounts/:accountId/merit-penalties/:penaltyId/end` `{ reason }`. Staff list payloads (users management, jobs / marketplace moderator account context, ticket case summary) carry `meritPenalties`.

## Standing punishment library

- `GET /api/admin/punishment-catalog?desk=&kind=` lists live named bans, suspensions, and timeouts for a desk. Same payload on `GET /api/moderator/punishment-catalog`. `kind` is `ban`, `suspend`, or `timeout`. `durationDays` is null when the default is permanent.
- Admin CRUD: `GET/POST /api/admin/punishment-defs`, `PATCH/DELETE /api/admin/punishment-defs/:punishmentDefId`. Body `{ label, kind, category, durationDays, permanent, desks, note }`. Duration 1–365 days, or `permanent: true` / `durationDays: null`. Ban rows are limited to admin and support desks. Delete is a soft-delete.
- Staff `PATCH /api/admin/accounts/:accountId/status` and moderator restriction patches require `punishmentId` for ban, suspend, and timeout. Catalog duration is used unless `customDuration: true` with `duration` / `endsAt` / `days`. Reason is still required. Lock and lift actions do not use the catalog. For a team target, ban / suspend / lock and their lifts take `memberScope`: `none` | `leader` (default) | `selected` (with `memberAccountIds`, active members of that team, max 500; otherwise 422 `TEAM_MEMBERS_REQUIRED` / `TEAM_MEMBER_NOT_FOUND`) | `all`. The older `includeLeader: true|false` still maps to `leader` / `none`. The response carries `members` (per-member result) and `leader`.
- The row must be on the issuer's desk, like warnings (`resolveIssuedPunishment` with `actorRole`; 403 otherwise). Admin and Support may issue any row. The dispute conviction ban keeps its own guard and skips this check. The actor's role comes from the staff row behind `staffId` or, for moderator sessions, `actorAccountId`; only system paths with neither count as Admin.
- A custom clock on a suspension or timeout ends within 365 days (400 past that), and only Admin or Support may make one open-ended (`duration: 'permanent'`, 403 for specialists, who lock instead). Appeal follow-ups are checked against the same rules before the decision is saved.
- Both catalog endpoints list a specialist's own desk whatever `?desk=` says (`catalogDeskFor`), so pickers never offer rows the issue path refuses.

## Platform view moderation

- `GET /api/staff/platform-view/context?path=&pick=` (every User & Team role) says what the framed member page is about and what the viewer may do there. `path` is a member path (`/profile/:id`, `/teams/:id`, `/forums/group/:id`, `/forums/discussion/:id`, `/jobs/postings/:id`, `/gigs/services/:id`, `/assets/:id`, `/disputes/:id`; other pages have no subject). `pick` is an item key from member markup: `forum_comment:<discussionId>:<commentId>`, `forum_discussion:<id>`, `forum_group:<id>`, `account:<id>`. Returns `{ path, page { kind, label, pickable }, subject, accounts[], contentActions[], reports[], recentActions[], viewer, limits }`. `subject` is read on the server (staff detail, so hidden text is still there), with `area` (`forum`, `marketplace`, `jobs`, `account`, `dispute`), state, evidence text, `notes` and `readOnly`. Each account carries its `CaseAccountSummary`, its team leader for team accounts, and `actions.{warn,timeout,suspend,lock,ban}` as `{ allowed, reason, note }`.
- `POST /api/staff/platform-view/actions` body `{ path, pick?, subjectKey, reason, contentAction?, accountId?, accountAction?: { type, warningId?, punishmentId?, customDuration?, duration?, endsAt?, includeLeader?, memberScope?, memberAccountIds? }, confirmRecent? }` (team member scope as on the admin status patch). Route limit `platformViewAction`: 20 a minute per account. The service re-reads the page and refuses when `subjectKey` no longer matches (409 `SUBJECT_CHANGED`), when the item is gone (409 `SUBJECT_UNAVAILABLE`), when the content action no longer applies (409 `CONTENT_ACTION_STALE`), or when a rule says no (403 `ACTION_NOT_ALLOWED` with its reason). Before anything changes it also checks the named warning or punishment, the target guards and the clock. A staff standing action on the same account in the last 10 minutes, or on the same item in the last day, returns 409 `RECENT_ACTION` with `details.recent` until the request repeats with `confirmRecent: true`. One action per account runs at a time (Redis lock, 409 `ACTION_IN_PROGRESS`; fails open without Redis). Case notes run 10–500 characters.
- Order: the content action first (hide comment, remove or lock a discussion, archive a group, delist or re-review a listing, pause or close a posting), then the account action through `warnAccount` / `updateAccountStatus`. If the content action fails nothing else happens; if the account action fails afterwards the response is `success: true, partial: true` and names which half went through. The response carries the refreshed `context` and `reportsOnItem`.
- Area rules: Admin and Support act on any item. A specialist acts on their own product's items and on profiles and teams. Content actions follow the desk routes (Admin plus Forum, Marketplace or Jobs & Gigs). Dispute pages are read-only: those penalties are decided in the dispute case. Staff targets need Admin, nobody acts on their own account, a suspension or lock never replaces a stricter ban or lock, and an existing suspension or timeout is changed in User & Team instead.
- Every audit row the action writes (`ACCOUNT_WARNED`, `ACCOUNT_STATUS_CHANGED`, `FORUM_TIMEOUT`, team rows, forum, listing and posting rows) gets `source: 'platform_view'`, `sourcePage`, `subjectKey`, `evidenceKind`, `evidenceTitle`, `evidenceExcerpt`, `evidenceHref`, `evidenceStatus`, `evidenceCapturedAt`, `relatedReports` and `pairedAction`, captured before anything changes. Desk services take these as a separate `audit` argument (`activityContext` for warn and status), never from a request body, so no client can forge them. Appeal case context (`record.warnings[].evidence`, `record.history[].evidence`) returns them for appeal review.
- Listing review (`reviewMarketplaceListing`, both Marketplace Control routes) and posting moderation (`updateJobsGigsPosting`, both Jobs & Gigs Control routes) write only from the state they read. Re-applying the current listing status is 409 (it used to re-notify the seller), and a change made meanwhile by another moderator is 409 instead of a silent overwrite.

## Contract disputes

- `POST /api/contracts/:contractId/dispute` creates a hidden Contract dispute, links remaining contract escrow through `related_dispute_id` / `related_credit_transaction_id`, and freezes release/refund until the case is closed.
- An ended contract (`Done`, `Completed`, `Closed`, `Cancelled`, `Rejected`, `isContractEnded` in `backend/lib/DisputeEscrow.js`) can still be disputed, to report conduct. The case stores `contract_ended_at_filing = true` (served as `dispute.conductOnly`): its milestone payments are final, so `settle_escrow` and `reverse_transaction` return 409 `CONTRACT_ENDED_NO_REFUND`, and case-file transactions come back with `reversible: false` and that reason. Staff can still record an outcome, dismiss, or sanction (ban). The flag is a filing-time snapshot, not the current contract status, because a settlement ends the contract itself and withdrawing that ruling must still allow a new settlement.
- One open dispute per contract, from either side: the advisory lock + existence check in `createContractDispute` and the partial unique index on `disputes(contract_id)` both reject a second one with 409. `GET /api/contracts` returns `active_dispute` to **both** parties so the other side sees the contract is already disputed and the UI blocks the form. For a private case the non-filer gets `id: null` and `number: null` (they learn only that a dispute exists); `viewerRole` (`disputer` | `disputee`) and `filedByViewer` drive the wording. Frontend helpers live in `frontend/src/pages/user/contracts/contractDispute.ts`.
- Filing limits on top of that (`disputeFilingBlock` in `backend/lib/DisputeEscrow.js`, checked under the same advisory lock): each side files at most **one dispute per contract** (counted by `by_account_id`, deleted cases excluded; 409 `DISPUTE_ALREADY_FILED`). The ruling is final, and something new goes through staff Reopen — until both parties choose to continue the contract after that case, which starts a new round where each side may file again. While the parties are still choosing, filing returns 409 `DISPUTE_DECISION_PENDING`. An ended contract can be disputed only until **30 days** after `contracts.ended_at` (`DISPUTE_FILING_WINDOW_DAYS`; 409 `DISPUTE_WINDOW_CLOSED`). While a closed case on the contract (by either side) still has a `dispute_payouts` row `scheduled` or `failed`, no new dispute can be filed (409 `DISPUTE_PAYOUT_PENDING`): those credits are earmarked for the ruling and a second case could split them again. The permanent blocks are reported before this one, and the payout's dispute number is named only when the viewer may open that case. The filing endpoint returns the block's `code` beside `message`. There is no unique index for the per-side rule because `swap_parties` can legitimately leave one account as disputer on two cases. `GET /api/contracts` returns `dispute_filing` per contract for the viewer: `canFile`, `code`, `reason`, `endedAt`, `windowEndsAt`, `previousDispute` (the viewer's own earlier case, same shape as `active_dispute`), and `pendingPayout` (same shape plus `payoutStatus` and `releaseAt`; `id`/`number` null when the viewer cannot open it). It is `null` before migration `1828800000000_contract-ended-at` runs.
- **Contract during and after a dispute** (`services/ContractDisputeHoldServices.js`, SQL in `repositories/ContractDisputeHoldRepositories.js`):
  - **On hold** while a dispute on the contract is open, a ruling's payout on it is still `scheduled`/`failed`, or the continue-or-end question below is pending (`contractOnDisputeHoldSql` in `lib/DisputeEscrow.js`). Escrow is frozen (approve, release, refund, cancel, cancellation requests and revision purchases return 409 `DISPUTE_ESCROW_FROZEN`) and the clock is stopped: the overdue, stalled, abandoned, auto-approve, deadline/review reminder and cancellation auto-approve jobs skip the contract. Work can still be submitted and discussed. `contracts.dispute_hold_since` marks when the hold began (set in the filing transaction).
  - **Continue or end after the case closes:** when a case closes without a ruling that ends the contract (resolve, dismiss, convict, a reversal once its payout is paid), the contract does **not** resume by itself. A `contract_dispute_decisions` row (`pending`, `decide_by` = 72 h) asks both parties, and the contract stays on hold. Both parties get `CONTRACT_DECISION_NEEDED` (and `CONTRACT_DECISION_REMINDER` 24 h before the deadline if they have not answered); the contract page, contract card and a banner on the contracts list show the prompt. `POST /api/contracts/:contractId/dispute-decision` `{ choice: 'continue' | 'end' }` (either party, via their actor accounts; 403 `NOT_A_PARTY`, 409 `DECISION_NOT_PENDING`):
    - **Continuing needs both.** The second `continue` closes the question as `continued`, resumes the contract and starts a **new dispute round**: disputes filed before it no longer count toward one-per-side (`disputeRoundStartSql`), so either party can dispute again.
    - **Ending needs one.** `end` cancels the contract in the same transaction under the cancellation rules (`cancelContractAndRefundInTransaction`: approved milestones stay paid, unfinished milestone escrow goes back to the client, gig order cancelled, workspaces archived, a pending cancellation request withdrawn); question `ended`, `CONTRACT_ENDED_AFTER_DISPUTE`.
    - **Nobody ends it by `decide_by`:** it continues (`auto_continued`); silence never moves money. A cancellation request from before the dispute is withdrawn only when both explicitly continue.
    - **One side continued, the other is silent:** at `decide_by` the silent side first gets **one** 48 h extension (`DECISION_EXTENSION_HOURS`): `decide_by` moves, `extended_at` is set, `reminded_at` is cleared so the 24 h reminder fires again, and both parties get `CONTRACT_DECISION_EXTENDED`. If the extended deadline also passes, it continues (`auto_continued`). Both silent → continues at the first deadline, no extension.
    - **Delivered work is reviewed, not dodged:** the client cannot `end` while work the freelancer submitted *before the question opened* still waits for review (409 `REVIEW_PENDING_WORK`, listed in `reviewPending`); they approve it or request a revision first. Approving stays allowed during the question (`allowDecision` on the approval guards); a contract that completes that way closes the question. Work submitted after the question opened does not block, so it cannot be used to trap the client. A freelancer may end at any time; the confirmation warns that their unapproved work goes back to the client.
    - While the question is pending: other money actions return 409 `CONTRACT_DECISION_PENDING` (the escrow guard), filing returns 409 `DISPUTE_DECISION_PENDING`, and jobs skip the contract. A reopened case or a contract ended another way supersedes the question (parties get `CONTRACT_DECISION_WITHDRAWN` on reopen); a choice that lands on such a stale question closes it and returns 409 `DECISION_NOT_PENDING` without acting. A case staff deleted resumes the contract without asking.
    - `GET /api/contracts` adds `dispute_decision` (pending only): `id`, `decideBy`, `extendedAt` (set once the extension was used), `viewerSide` (`client` | `freelancer` | null for team members who cannot decide), `viewerChoice`, `otherChoice`, `reviewPending` (`[{ id, name }]`), `dispute` (id/number only when the viewer may open the case).
    - Staff dispute detail adds `contractAfterCase` (`contractStatus`, `onHoldSince`, and the case's latest `decision` with both answers and its resolution), shown as "Contract after this case" in the dispute console.
  - **Resume:** when the contract continues (both continue, nobody ended it in time, or a deleted case), every clock moves forward by the time spent on hold: `contracts.deadline_at`, started unfinished milestones' `deadline_at` and `overdue_at` (a milestone whose new deadline is in the future goes back to `active`), `milestone_submits.review_paused_for` (added to the auto-approve and review-reminder windows), and pending cancellation requests' `auto_cancel_at`. Each counts only the part of the hold it lived through. Both parties get `CONTRACT_RESUMED`.
  - **Settlement ends the contract when it is ruled** (`endContractAfterSettlement`), not when the payout is paid: `Closed` when a milestone was approved, else `Cancelled`; unfinished milestones and the gig order are cancelled and team workspaces archived. The payout still lands on its date and escrow stays frozen until then. What changed is kept in `contracts.dispute_settlement_end`, so `cancel_payouts` restores the contract, milestones, gig order and workspaces exactly, back on hold under the reopened case.
  - A reversal ruling keeps the contract on hold until that payout is paid; then the parties are asked to continue or end it.
  - A settlement ruling also withdraws a pending mutual cancellation request (restored with the contract if the ruling is withdrawn).
  - Sync points: the filing transaction, and `emitDisputeState`, which syncs the case's contract before every broadcast. The 5-minute job `reconcileContractDisputeHoldsServices` catches the rest, continues expired questions, sends the 24 h reminders, and ends live contracts whose settlement ruling still stands (rulings made before settlements ended contracts at once, notifying `CONTRACT_ENDED_BY_DISPUTE`).
  - `GET /api/contracts` adds `dispute_hold`: `since` (null when not on hold) and `settlement` (`id`, `number`, `visibility`, `status`, `filedByViewer`, `endedAt`; id/number null when the viewer cannot open the case) when a settlement ended the contract. Null before migration `1829900000000_contract-dispute-hold`. The contract page shows the hold, pauses the milestone countdown at the time left when the hold began, and explains a settlement end; frontend helpers are `contractHoldState` / `contractHoldDetail` in `contractDispute.ts`.
- `action: "swap_parties"` (assigned handler or Admin, open cases only) swaps `by_account_id` and `for_account_id`, with optional `reason`. In the same Postgres transaction it runs `swapDisputePartyLabels` on the Mongo chat, flipping `disputer` ↔ `disputee` in each message's `audience`, `audiences` and `author_role`, so every message stays with the person it was written for. If the commit fails, the Mongo flip (its own inverse) is reverted. It then posts a system "Parties swapped" notice (`public` when visible, else `disputer`), records activity for both accounts, notifies both parties and emits `disputeUpdated` with `reason: "parties_swapped"` so open member pages re-read their role. The swap refuses to run while MongoDB is down (503), so the notice can always be posted. Escrow and payouts are contract-based and do not move. On a private case the old filer loses access, and the new disputer gains it (including the original complaint).

Approved milestones already paid out of escrow can't be picked. - Staff report PATCH: `action: "sanction"` takes `sanctionType` (`warning` | `timeout` | `suspend` | `lock` | `ban`), `reason`, `days` (required for `timeout` and `suspend`; optional for `lock`, which otherwise lasts until unlocked; 1–365) and optional `warningId` (named warning, desk-checked; default `staff_follow_up`). Role rules match `UserTeamPermissions.allowedStatusActions` (403 otherwise); `timeout` only applies to forum report types (400 otherwise). Reports whose detail has `sanctionable: false` (technical problems) return 409 on sanction. Hand edits accept `status` in `open`, `in_progress`, `under_review`, `escalated`, `closed`, `resolved`, `dismissed` and `priority` in `low`, `medium`, `high`; `sanctioned` / `denied` are decision-only and final (409 when changing a decided report). `action: "self_assign"` is guarded in SQL (409 if someone else just claimed it).
- Staff `GET /api/admin/reports/:id` and the matching moderator report detail routes return `subject` with `headline`, `preview`, `available`, `linkable`, `links`, and (for chat) `message`. `links` are member-site paths; staff consoles wrap them in platform-view. Inbox messages are not linkable, so the snapshot body is shown instead. Deleted jobs, gigs, assets, discussions, groups, and teams keep the snapshot and drop the dead Open link. Forum reports add `subject.forumContent` (`kind` `discussion` | `comment` | `group`, live `status`, `removedBy`, `removalReason`, and `currentText` when the author edited the item after the report); staff consoles use it to remove the discussion, hide the comment or archive the group through the existing forum moderation PATCH routes.
- The same detail GET routes also return `sanctionTypes` (what the viewer may apply from this report) and, for sanctionable reports, `reportedContext` (`getReportedAccountContext` in `TicketCaseRepositories`): `standing` (the case account summary), latest `warnings` and `restrictions`, `recentActivity` (account activity without report-handling rows), `otherReports` against the account, `forum` (forum reports only: totals, groups joined / owned / banned from, latest discussions and comments, including ones moderation removed) and `notes` for sections that failed to load. PATCH responses do not include `reportedContext`.

## Marketplace license endpoints

- `POST /api/assets/:assetId/purchase` returns `license` alongside the existing purchase response. `alreadyPurchased` means an active unassigned license was reused without another charge. Asset responses include `available_license_count`; `is_purchased` still means the viewer has at least one active purchased license.
- `GET /api/assets/:assetId/licenses?page=1` returns the authenticated buyer's license history, 50 records per page with `hasMore`.
- `POST /api/assets/:assetId/licenses/:licenseId/assign` accepts `{ "projectId": "uuid" }`. Only the buyer can assign their active license, and they must be an Owner, Manager, or Editor of a non-deleted, non-frozen project. Repeating the same assignment succeeds; changing projects or consuming another license for an already-licensed project returns 409.
- Original preview/download routes accept optional `projectId` query context for shared project access. Without that context, existing creator/buyer library access remains available. Render source authorization uses the internal `render-source` action described below.

### Editor asset checkout

- Editor `/api/market-assets/:id/purchase` GET loads the asset, current wallet balance, available unassigned license and current project license. POST requires the current project, confirmed asset price and confirmed charge. It reuses an available license or purchases and assigns one atomically. Another collaborator/retry finding the project already licensed returns without charging again.
- Both editor routes verify the signed editor session and forward its account identity through the existing internal-secret bridge. Browser POST requests require matching Origin. Editable project membership and frozen-project rules are enforced on the backend.
- `/api/market-assets/licenses?projectId=...&ids=...` reads project licensing for timeline badges and playback, after verifying current membership. Licensed assets include `imageSources`, keyed by media asset ID, so images download directly from storage without another authorization/redirect round trip. Original paths come only from linked, non-deleted image files under assets with active project licenses. The response is private/no-store and exposes database/signing durations through `Server-Timing`. With protected CloudFront enabled, original image/video/audio playback uses exact-file CloudFront grants lasting 55–60 minutes. Signed S3 remains the fallback only when CloudFront is disabled or a legacy key is outside its protected asset-originals/ path; legacy S3 images retain their 30–60-second grants. Status refreshes on project/items change, purchase, window focus and periodically for collaborators.
- Playback uses one batch license loader, including nested scenes. Existing licenses are published without waiting for unrelated free-use claims. Only mounted image layers request their bytes; each image is decoded before it appears. A project-scoped cache deduplicates by stable playback source, independent of rotating signed URLs, and releases bytes when a source is removed or the project unmounts. The canvas always stays mounted; videos/audio stream independently. Neither signed URLs nor blob URLs enter project history.
- Editor `/api/market-assets/:id/source?projectId=...&mediaAssetId=...` validates the signed editor session, project membership, active project license and exact asset/media linkage through the same repository and signing service as the batch endpoint. It returns a private/no-store 307 redirect using the same CloudFront-first delivery policy. A failed CloudFront signing attempt for a protected original fails closed rather than falling through to an S3 redirect. The browser downloads bytes directly from the CDN; the editor server does not relay them. Issued grants remain usable until expiry. Export source authorization is described below.

- Creator ownership is returned separately from project `licensed` status. For paid assets, merely reading/selecting an asset never grants a project license or unlocks editor originals. Explicit creator checkout with a confirmed zero charge grants a project license without a ledger transaction or wallet changes. Project-context original previews require that project license, including for the creator; standalone creator library access is unchanged.

- Editor `POST /api/market-assets/:id/use-free` runs for free assets present in a project, including drops and nested scenes. It verifies the signed session, editable membership, non-frozen project and published asset, then checks the current zero price under lock and saves a zero-cost project license without a payment or wallet mutation. Existing project licenses are reused even after a price increase. Paid creator assets still require explicit owner-discount checkout; client snapshot prices never authorize free use.
- Free project licenses share the purchased-license access checks, retaining clean editor playback for collaborators after listing price increases. Free items have no timeline price badge or canvas purchase control. Free project licenses also authorize clean export sources.

### Export assets and draft flow

- The export dropdown inspects visible IDs in the current project or scene, including one embedded scene-content layer as the renderer does. It excludes hidden/orphaned items and counts each marketplace listing/bundle once. License status is refreshed before presenting the export action.
- Unlicensed paid assets show primary Pay for assets in the project/scene and outline Get watermarked draft actions. The purchase modal quotes all distinct assets, displays owner discounts/available licenses and the total, and requires explicit confirmation. Each checkout retains the existing server-side price/charge guards and idempotency. If a later checkout fails, committed licenses remain and the modal re-quotes the remaining balance before another confirmation; the overall batch is not one atomic transaction.
- Editor export requests carry projectId and an explicit marketDraft flag. The signed editor session supplies the render identity (including status/cancellation requests); client identity headers are not trusted. Internal render-source checks membership and the actual project license for every market media file. Licensed media uses protected originals; unlicensed media is rejected for clean export and uses a validated generated proxy only for explicit drafts. Export never makes a purchase.
- Render source URLs expire after 24 hours to allow queueing and are inserted only into the render job copy, never project history. The render server progress endpoints return only format/type/project name from job input and redact raw error details; they do not expose source URLs. Existing 60-second preview/download URL expiry is unchanged.

## Rate-limit monitor

- `GET /api/admin/rate-limits` (Admin, `no-store`) returns the in-process monitor: per-minute allowed/blocked history for the last 60 minutes, per-policy totals, live windows sorted by usage (`active`, each with its Redis `key` and `scope`: `account`, `device` or `ip` for the signed-out network ceiling), `sharedIps` (addresses used by several accounts or signed-out browsers, with the highest network-ceiling usage), recent 429 `events` (retries of one request within a minute are grouped as `repeats`), `policies`, the counter `store` (`redis` or `memory`), limiter `storeErrors` and `clientIp` (how the API resolved the caller's IP against `CF-Connecting-IP` / `X-Forwarded-For`).
- `POST /api/admin/rate-limits/reset` `{ key }` deletes one live window. The key must match `rate-limit:v2:<policy>:(acct|dev|ip):<subject>`; anything else is 400.

## Analytics

- `GET /api/admin/analytics-overview` (Admin, `no-store`) goes through `AdminAnalyticsServices`. Query: `range` = `7d` | `30d` (default) | `90d` | `12m` (from the first of the month 11 months back) | `ytd` | `all` | `custom` (+ `from`, `to` as `YYYY-MM-DD`, at most three years, `to` clamped to today); optional `bucket` = `day` (ranges ≤ 92 days) | `week` (≤ 3 years) | `month`, default by length; `refresh=1` skips the cache. Malformed values return 400 `ANALYTICS_INVALID_REQUEST` rather than showing a different period.
- The response covers that range and the same-length period right before it (`range.previous`, null for `all`): `summary` KPIs as `{ value, previous, changePct }`, a per-bucket `series` (signups, distinct active members, tickets, reports, listings, top-ups, subscription revenue, net fee credits, cashouts; first/last buckets may be `partial`), `members`, `engagement`, `community`, `money`, `operations`, `alerts` (each with an admin `href`) and `problems` (sections whose query failed; such a result is not cached).
- Money rules (`AdminAnalyticsRepositories.js` header): top-ups are PAID `TOPUP` payments by paid date; subscription revenue is SUCCEEDED/PAID invoices by `paid_at` plus `SUBSCRIPTION` upgrade payments; fee revenue is Completed fee rows minus Completed fee refunds (reversed fees excluded); cashouts are SUCCEEDED net PHP by request date. MRR uses list prices of members with an active paid subscription.
- `engagement` comes from `account_active_days` (see `docs/database.md`): DAU / WAU / MAU as of today, distinct actives in the period, stickiness (average daily actives over the last 30 tracked days ÷ MAU) and eight weekly signup cohorts. Before the migration or before any activity it is `{ available: false, reason }`. Comparisons are hidden while the previous period predates tracking.
- `community` aggregates whole MongoDB collections (banned group members and deleted comments excluded) and resolves discussion authors to names. `{ available: false }` when MongoDB does not answer.
- `GET /api/admin/analytics/finance/:kind` (Admin), `kind` = `topups` | `invoices` | `subscriptions` | `cashouts`: server-paged (`page`, `limit` ≤ 100), filters `status` (per-kind groups such as `paid`, `in_flight`, `failed`), `channel` or `plan`, `search` (≤ 100 characters, LIKE wildcards escaped), `from`/`to` (not for subscriptions). Returns `{ items, total, sumPhp, page, limit, pages }`. Cashout account numbers are masked to the last four digits. `format=csv` downloads up to 5,000 newest matching rows (`X-Export-Rows`, `X-Export-Total` headers); cells starting with `= + - @` are prefixed with `'` so spreadsheets do not run them.
- `GET /api/admin/analytics/finance/options` lists plans and the top-up and cashout channels seen, for those filters. The old unpaged `analytics/platform-transactions`, `user-transactions` and `topup-transactions` endpoints are gone; credit movements live in the Credits & Economy ledger.

## System settings

- `GET /api/admin/settings-overview` (Admin) returns `sections.{platform,economy,security}` (`value`, `updatedAt`, `isDefault`, `version`), `defaults`, `rules` (bounds the form mirrors), `feeUsage` (how each fee row is actually charged; `unused` rows are not collected anywhere), `staff` (role, `hasAuthenticator`), `changeHistory`, `alerts` (with `tab`), `viewer.ip`, `delivery.email` and `propagationSeconds`. Package `salesCount` is computed from PAID top-ups at that package's credits and price; it is never stored.
- `PATCH /api/admin/settings` `{ section, values, baseVersion? }` goes through `AdminSettingsServices`. `values` may be partial; it is merged over the stored section while that section is locked. Unknown keys are dropped. Invalid values return 400 `{ code: 'SETTINGS_INVALID', errors: { <path>: message } }` (paths like `sessionTimeoutDays`, `creditPackages.<id>.pricePhp`, `feeSettings.<id>.percent`). A `baseVersion` that no longer matches returns 409 `SETTINGS_VERSION_CONFLICT`. Success returns the fresh overview plus `changed` and `changeCount`.
- Each save that changes something writes one `SETTINGS_UPDATED` `account_activity` row (account = the admin's account, actor = staff, `metadata.changes` = field before/after), in the same transaction under a savepoint.
- Fee label, description and payer come from `DEFAULT_SETTINGS`; only `percent` / `flatFee` are editable, and only where `feeUsage` says they are charged. `fee-marketplace.percent` mirrors `marketplaceSettings.transactionFeePercent`.
- Active credit packages need distinct credit amounts (top-ups match a package by credits). The legacy `TOPUP_PACKS` only apply when the economy configuration cannot be read.
- `sessionTimeoutDays` is capped at 30 because the `sessionId` cookie lasts 30 days from sign-in.
- `GET/PUT /api/admin/subscriptions/plans[/:id]` (Admin): PUT takes `{ description, price, days_of_trials, features? }` and saves plan and features in one transaction, logging `SUBSCRIPTION_PLAN_UPDATED`. Names cannot change (code finds tiers by name), the free plan stays at ₱0 with no trial, paid plans cost ₱1–₱100,000, and feature values are at most 100 characters. `PUT /plans/:id/features` remains for older clients.

## Support tickets

- Members file their own tickets with `POST /api/users/tickets`. The requester is always the signed-in account. `fields` holds that type's answers. A project, listing, order, contract, or job picker sends the record id; the server stores the name beside it and rejects an id the account does not own. The Teams type sends a team id from `GET /api/users/ticket-teams?q=`, which returns public teams plus any team the account has a membership on, including private ones. The server stores that team's name and id, and rejects a team the account cannot see. `context` (`browser`, `device`, `page`) is stored with the account snapshot on the ticket. Ticket detail returns `formValues` and `submissionContext` separately. The contract picker lists job contracts and gig orders (labelled with the other party and status); the job picker lists jobs the member posted or applied to, and their gigs; the listing picker lists one row per asset (its latest listing). Listings, contracts and postings include those held by teams the member owns (`getAuthorizedActorAccountIds`), as on their own pages.
- Asset and job-or-gig search pickers (`picker: 'asset' | 'posting'` in `lib/TicketFormFields.js`) use `GET /api/users/ticket-search?kind=asset|posting&q=&scope=others` (≤ 80 characters, or a pasted link with an id; 8 results `{ id, label, detail }`). Assets: published and not trashed, plus the member's own and ones they bought; an empty `q` lists what they bought (and own, without `scope`). Postings: jobs and gigs that are not deleted (gigs not archived), plus the member's own; an empty `q` lists jobs they applied to and gigs they ordered. `scope=others` leaves out the member's own items. On submit the server stores the item's label and id, refuses an id the member cannot see (400) and, for `pickerScope: 'others'` fields (reports), the member's own item (400). A typed name or link is stored as typed; a link naming a visible item is matched to it. Marketplace "Report a listing or seller" and Jobs "Report a listing or user" ask `report_target` first, then the item (`listing`) or the username (`seller_username` / `reported_username`). "Asset reviews" picks the asset, "Gig reviews" the contract, and the marketplace and jobs appeal types may name the listing, job or gig (`listing`, optional); the staff case context shows each.
- Member intake rules live in `services/TicketServices.js` (`createMemberTicket`). `type` must be a catalog type (or a legacy label that maps to one); subject is 1–200 characters and description 10–5,000 for every member ticket. Priority is always the type's default and the stored email is the account's own: the body's `priority` and `email` are ignored. The same open ticket (account, type, subject) filed again within 10 minutes returns 409 `{ code: 'TICKET_DUPLICATE', data: { ticketId, ticketNumber } }`. The route has the `ticketCreate` limit (15 new tickets per hour per account). Errors below 500 carry a member-facing `message`; anything else is a generic 500.
- Member ticket attachments (new tickets and replies) must be files the author's own account uploaded and finalized (`upload_intents` consumed, `listOwnedUploadKeysRepository`), at most 4 per message. Any other key returns 400 instead of being dropped, and a new ticket checks them before its row is written. Staff messages keep the plain key check.
- Staff ticket detail (`GET /api/admin/tickets/:id` and each moderator desk's `GET …/tickets/:id`) adds `caseContext` only with `?include=case`, built by `repositories/TicketCaseRepositories.js` after the desk's own scope check. It is read-only, each section fails on its own into `caseContext.notes`, billing data follows `canViewTicketPayments`, and it never returns verification links or documents, or other members' emails. Dispute detail for staff adds `caseFile.parties` (both sides' standing) and `caseFile.relatedTickets` (tickets naming the dispute's contract). Each `caseFile.contracts[]` entry, and the ticket case `contract`, carries `gigOrder` for gig orders (null for job contracts): `{ requestId, tierTitle, tierCredits, tierDeliveryDays, tierRevisions, addons[{ id, name, priceCredits, additionalDays }], addonCredits, addonDays }` (`gigOrdersForContracts`). Add-on rows are never edited in place, so their price is what the order paid; the tier price is the tier's current one. The ticket case `contract` also has `requesterViaTeam`.
- Ticket state: status and priority changes, and scheduling a close, need the assigned handler or Admin (an unassigned ticket may be triaged by its queue). Claiming is guarded in SQL, so two staff claiming at once get a 409 for the second. An undecided appeal ticket returns 409 on close or scheduled close: decide it with `POST /api/staff/tickets/:id/appeal-decision` (Admin, or the Support Moderator assigned to it). Body: `decision` (`accept` | `deny` | `deny_permanent`), and optionally `remedy` (`lift_24h` default, `lift_now`, `shorten` with `endsAt`; ignored for warnings, which are rescinded), `note` (≤ 1,000 characters, shown to the member) and, on a denial, `followUp: { action: 'suspend' | 'ban', punishmentId, reason, days? }` (`days: null` = permanent ban; omitted = catalog length). The response adds `appealOutcomeSummary: { outcome, followUp }`. A decided appeal returns 409 on any status change that would reopen it.
- Appeals are per penalty. `GET /api/users/appeals` (members; on the banned/locked allowlist) returns `{ perPenalty, legacyOpenAppeal, penalties[] }`, each penalty with `type`, `id`, `label`, `detail`, `reason`, `number`, `startedAt`, `endsAt` and `appeal: { state, canAppeal, ticketId, ticketNumber, availableAt, message }`. Filing sends `appealTarget: { type, id }` with `POST /api/users/tickets` (type "Appeal an account penalty"); staff opening one for a member send it to `POST /api/staff/tickets` and list the member's penalties with `GET /api/staff/tickets/appeal-options/:accountId`. Ticket payloads carry `ticket.appealTarget`; the staff detail also carries `appealOutcome` and `appealDecisionNote` (the member read drops `appealOutcome`). The decision is a chat message with `messageType: 'appeal_decision'` and a structured `decision` card. Inactivity auto-close runs only when staff spoke last and never on an undecided appeal; `autoClosesAt` follows the same rule.
- Ticket credit adjustments are one atomic, relative wallet update in a transaction (no lost updates), whole numbers up to 1,000,000, never on the staff member's own account or a closed ticket, and the ledger row references the ticket.
- `GET /api/transactions/credits` also lists dispute payouts that are scheduled to land in the member's wallets, as `status: "Pending"` entries with `pending` (`releaseAt`, `paused`, `failed`, `disputeNumber`); `walletSummary.pendingCredits` sums them. They never count toward balances.
- Staff open a ticket for someone with `POST /api/staff/tickets`. Admin can use the same body on `POST /api/admin/tickets`. Body: `{ requesterAccountId, subject, type, description, priority?, assignToMe? }`. `requesterAccountId` is required and must be a live member or staff account. Description is stored as the opening staff message. `assignToMe` only succeeds when that staff role can handle the ticket type; otherwise the ticket stays unassigned in the type's queue.
- Staff search accounts with `GET /api/staff/tickets/people?q=`.

### Editor sharing and template handoff

- Published template previews open on the editor at `/preview/:marketAssetId`. Each request resolves the currently published, non-deleted listing and renders the existing sanitized, watermarked preview without caching the page. Main-site navigation retains the editor session handoff; its query token is stripped before the preview opens. Legacy encrypted market preview links still enforce their snapshot binding and expiration. Public `GET /api/assets/:assetId/template-preview` continues returning saved-snapshot dimensions, duration, and the legacy encrypted preview token for compatibility.
- `GET /api/assets/:assetId/template-use` prepares a template-use quote (current price, actual charge after any available license/creator discount, and whether the captured content contains paid marketplace assets). `POST` takes `projectId` as a retry key plus `expectedPrice` and `expectedCharge`. It always creates a new project, or returns the already-created project for that same authenticated buyer and template; it never overwrites an existing project. Project/scenes, owner memberships, upload references, license assignment and payment commit in the existing checkout transaction. No migration is required.
- Template purchase uses the regular purchase endpoint and leaves the license unassigned. The resulting Use in a project CTA opens a separate confirmation explaining the new project and permanent license assignment. Opening it makes no preparation or wallet requests. The paid-assets tip is an inline details-page card, alongside the existing earnings and used-license notices. Project-creation troubleshooting is deferred at the user's request.
- The backend calls the editor's secret-authenticated `/api/internal/templates/prepare` endpoint to decode the saved template and scene snapshots at capture time. Copies get fresh scene IDs and documents without source collaboration history, members or licenses. Marketplace references remain intact and sources reset to generated watermarked proxies. Included uploaded media gets separate media records referencing the same files so storage cleanup preserves purchased copies.

- Editor `POST /api/projects/:id/share-link` accepts `{ role }` for Owner/Manager callers (only owners may grant Manager). It returns a main-site `/projects/open/:id?share=...` URL. Tokens expire after 30 days and use a purpose-specific derived signing key. After platform login/handoff, the editor verifies the token and current issuer role/membership before adding access. Existing members are promoted only when the signed role outranks their current role; lower-access links never demote them or alter Owner access. Promotions update the existing membership role without resetting joined_at, and the Share modal reflects that stored role. Token expiry does not undo redeemed membership; a still-valid link can promote a manually demoted member again. Changes commit before realtime access refreshes. No separate link-access storage or schema change is used.
- Editor `POST /api/projects/:id/template-snapshot` accepts the current Yjs document as an octet-stream, with `blockId` when editing a scene. It requires Owner/Manager access, rejects frozen projects, and checks scene editing permission. It compacts persisted/live project and scene state with current local edits and returns an Asset Library URL carrying the saved snapshot ID and project name.
- Template listing creation/replacement verifies that the snapshot belongs to a non-deleted project the asset owner currently owns/manages. Existing account eligibility, showcase uploads, listing moderation and snapshot reuse checks still apply; no new database columns are needed.
- Private create-template previews retain `/preview/:reference`, accepting an authenticated-encrypted reference issued when sharing a template, plus the existing editor handoff token. Numeric snapshot paths are rejected. The reference hides the snapshot ID, is bound to its issuing user, and expires after 30 days; current Owner/Manager access to the source project is still required. No database mapping or schema change is used. It reads only the selected snapshot, resolves scene snapshots at its capture time, and prepares media using existing project license authorization. The snapshot route renders the existing Editor in Viewer mode, with local snapshot/scene hydration and the same editor UI. It does not create a project or editing session, connect collaboration/comments sockets, or attach persistence; project-specific presence, purchase and export handlers are not mounted.

### Licensed collections and export settings

- `GET /api/market-assets?view=licensed&projectId=...&type=image|video|audio` lists assets with active, non-deleted licenses assigned to the current project. A signed session and active membership in a non-deleted project are required. The collection includes collaborator/free licenses and licensed unpublished listings; it excludes unassigned and other-project licenses. Existing search, bundle pagination and media counts apply.
- Export settings now use a separate asset-payment step when Export project/scene finds unpaid assets. Back restores settings; cancelling checkout returns to the asset step, while completing it returns to settings.
- Editor export dropdowns and `/api/render` validate `export_resolution` and `export_frame_rate` from the effective plan's database features. `/api/uploads/policy` supplies these limits and the other tiers' export limits for dynamic upgrade badges; editor upload normalization separately reads `video_upload_resolution`. Policy refreshes on export-panel opening, focus, and every 30 seconds, while submissions always query the current database limits. Missing/invalid values fail closed. Render-server rollout and composition deployment remain separate from upload normalization.
- MP4/MKV target bitrate remains capped in the UI, download state and editor export endpoint at five times the existing resolution/FPS/aspect-ratio recommendation, up to 96,000 kbps. Existing audio, GIF and ProRes bitrate handling is unchanged.
