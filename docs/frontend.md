# Frontend

## Stack and entry points

- React 18 + TypeScript + Vite.
- Entry: `frontend/src/main.tsx`; application routing/root: `frontend/src/App.tsx`.
- Shared API client: `frontend/src/lib/api.ts`.
- Shared Socket.IO client: `frontend/src/lib/socket.ts`.
- Shared global state exists in `frontend/src/lib/global_state.ts`; feature-local state may use Zustand or existing component patterns.

## Staff consoles

- Admin lives on `admin.ensemble.software` (`admin.localhost:5173` in dev). Staff lives on `staff.ensemble.software` (`staff.localhost:5173`). The main site redirects `/admin`, `/staff` and `/moderator` to those hosts, on page loads and on in-app navigation (`LegacyConsoleRedirect` in `lib/ConsoleRouter.tsx`). Browser paths omit the console prefix (`/dashboard`); route code still uses `/admin` and `/staff`. Moderator desks live on the staff host and keep their full path there (`staff.ensemble.software/moderator/support`), because `/support` and `/jobs` are also member pages.
- Point both console hosts at this same frontend build, and serve `index.html` for their client-side paths. The API allows those origins from `FRONTEND_URL`.
- Vite writes built files to `dist/static/` (`build.assetsDir` in `vite.config.ts`), not the default `assets/`, because `/assets` is the marketplace page. With a real `assets/` folder in `dist`, a full page load of `/assets` hit the folder on the host and returned 500.
- Each console host has its own session. Admin and staff call `/api` and `/socket.io` on their own host (`consoleApiOrigin`; the Vite proxy locally; the production proxy must forward both paths, WebSocket upgrade included, on `admin.ensemble.software` and `staff.ensemble.software`), so console cookies never reach the member site and a member login never signs a console out. Do not point a console host at the shared API host: its cookies would be overwritten by every member login in the same browser.
- The member site signs out any admin or staff session it finds and refuses admin and staff logins with a pointer to the right host. `consoleIdForAccount` (`lib/staffRoutes.ts`) decides the host: Admin → admin, every other staff role → staff.
- `/`, `/login`, `/signup`, `/forgot-password`, and `/reset-password` on the main site never auto-redirect a staff session into a console. Staff portal “Member login” links go to the main-site `/login`.
- Platform view and reported-item previews frame member pages from the console host itself (for example `admin.ensemble.software/forums`). Inside that same-origin frame no prefix mapping or redirect applies, so the preview keeps the staff session and the view-only guard. A console host framed by any other origin renders nothing.
- Platform view pieces: the console page `staff/StaffPlatformPreviewPage` (console accent and header, sections with the member sidebar's icons, Back/Reload/Start page, an address bar that takes paths, pasted member links or a people search — `@handle`, a name, or any word that is not a member route opens `/search/user/:query` — with `/` to focus it, desktop/tablet/phone preview widths, focus mode, open in a new console tab, Copy member-site link, a retry after 12 s without an answer, a note when the frame swapped a blocked page, `?path=` kept in sync with the frame so reloads and shared links return to the same page; width and focus mode are per-browser `localStorage` conveniences); `staff/StaffPreviewFrameBridge` in `App` (frame side, every route: follows `STAFF_PREVIEW_NAV_MESSAGE` including `action: "back"`, posts `STAFF_PREVIEW_LOCATION_MESSAGE` on every navigation, swaps blocked pages, routes this site's `window.open`/new-tab links into the frame, and runs `useStaffPlatformGuard` plus its hide style on every route, including the landing and not-found pages outside `Layout`); `useStaffPlatformGuard` (hides and blocks member actions, file drops and form submits except search forms — `isStaffPreviewSearchForm`: GET, one or two text fields with a search hint, no textarea or upload — and shows one "view-only" notice); `lib/axios.ts` (rejects writes except `/api/users/refresh-token` and the read-only `/api/users/list-of-details`, and reports a failed refresh with `STAFF_PREVIEW_SESSION_MESSAGE`). Allowed and blocked paths live in `lib/staffPlatformView.ts`: `ACTION_PATHS` (member tools and the staff account's own pages, e.g. `/projects`, saved/applied lists, inbox, contracts) fall back to their section's public page; console, sign-in, setup and appeal pages fall back to `/home`. A new member page that only makes sense for its owner belongs in `ACTION_PATHS`. A POST that only reads must be added to the axios allowlist or platform view breaks that page.
- Console links to member content open platform view, never the main site: use `staffPlatformViewHref(consolePath, memberPath)` (a `Link` with `target="_blank"` when the console context must stay open). The main site has no admin session.
- Platform view **Moderate** (toolbar toggle; open state is a per-browser `localStorage` convenience) opens `staff/platformView/PlatformModerationPanel` beside the frame (an overlay under `lg`). It follows the shown path, debounced, and asks `GET /api/staff/platform-view/context`. A stale answer never replaces a newer page. The panel shows the item and its state, item actions, each person's `StaffStandingSummary` with Warn / Timeout / Suspend / Lock / Ban (greyed with the server's reason), open reports with desk links (`consoleLinks`), and the last 24 hours of staff actions. `PlatformModerationActionDialog` (portaled to `body` inside `.staff-console`, because the phone overlay is `z-20`) takes an item action, an account action, or both, with the desk's warning or punishment picker, a custom clock (`SanctionScheduleFields allowPermanent={false}` for specialist suspensions and timeouts), the team-leader option and 10–500 character case notes. It shows what will be saved as evidence, and offers "Act anyway" after a `RECENT_ACTION` refusal. The member site never renders staff controls.
- Pick mode: member markup marks pickable items with `data-moderation-subject` (forum comment rows, post cards and group cards in `Forums` / `SelectedGroup`, plus the discussion article and comment cards in `ExpandDiscussion`). The attribute is inert for members. The console sends `STAFF_PREVIEW_PICK_MESSAGE { active }`. The frame (`useStaffPickMode`) outlines items, highlights the one under the pointer, swallows every click, and answers with `STAFF_PREVIEW_PICKED_MESSAGE { subject }` (null on Escape or a page change). The console keeps only keys that match `moderationSubjectKey` and drops the pick when the frame changes page. Mark a new item type the same way and add its resolver in `PlatformViewModerationServices`.
- Platform view uses `sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-popups-to-escape-sandbox"` (without `allow-forms` the browser never fires `submit`, so member search boxes were dead); the guard cancels every non-search form. The reported-item preview keeps the same sandbox without `allow-forms`. External links open in a normal tab (forced `noopener`); downloads stay blocked. The member onboarding tour and staff notification toasts never run for staff.
- `StaffMiddleware` requires the Admin role for every `/admin/*` route. The backend remains the authority: every admin API route uses `checkSession` + `requireAdmin`.
- Admin, moderator, and staff portal pages are registered in `frontend/src/pages/staff/staffPages.ts` with `lazyWithPreload`. Add new console pages there and to the matching console list, not as `lazyPage` entries in `App.tsx`. New admin pages also need their first path segment added in `frontend/src/lib/consoleHosts.ts`.
- Console layouts render `StaffOutlet`. It keeps the sidebar mounted behind a content-area loader and preloads the console's other pages once the browser is idle.
- Console navigation is `staff/ConsoleSidebar` for Admin and every moderator console: fixed sidebar from `md`, sticky top bar (`z-30`) with a slide-in drawer on phones (closes on navigation and Escape). On phones, `sticky top-0` page headers become static via CSS so only that bar stays pinned. First loads render `staff/ConsolePageSkeleton`, not a spinner.
- Console page shells (`main` or the page's root wrapper) are `relative` without a `z-index`. A `z-10` shell becomes a stacking context, so every dialog inside it renders under the sidebar and the phone top bar (both `z-30`), hiding the dialog's left side or close button.
- Console dialogs: an overlay is `fixed inset-0 flex items-center justify-center p-4` (add `md:pl-[260px]` to center it beside the sidebar), and its panel is capped with a `dvh` height (`max-h-[90dvh]`, not `vh`, which ignores mobile browser bars). `index.css` makes every `.staff-console` overlay `align-items: safe center` + `overflow-y: auto` and pins `absolute inset-0` backdrops to the viewport, so a dialog taller than the screen scrolls from its header instead of losing it above the viewport.
- Console motion lives in `index.css` under `.staff-console` (set on `AdminLayout` and `ModeratorShell`): page fade, staggered rise of the content's top-level blocks (`.console-stagger` for nested grids), modal backdrop fade + panel pop, press feedback, row hover, `.console-lift` cards, `.console-bar` grow, `.console-skeleton` shimmer. Only `opacity`/`transform` animate, and everything is off under `prefers-reduced-motion`. Entry animations must use fill-mode `backwards` (never `both`/`forwards`): an animation still in effect after it ends makes the element act as `will-change: transform`, which becomes the containing block and stacking context of every fixed dialog inside it, so dialogs render inside the card and slide under the sticky header. `staff/consoleMotion.ts` `useCountUp` animates KPI numbers with one rAF loop.
- Staff page and tab list/overview loads use `staffGet` and seed state from `peekStaffGet` (see `docs/caching.md`). Show the blocking spinner only when nothing is cached; a failed background refetch keeps the shown data. Add new mount-time GETs to `lib/staffPrefetch.ts`.
- Every console page, tab and modal that reads data is live: `useStaffLive(topics, reload, { delayMs, pollMs, enabled })` from `lib/staffLive.ts` (topics are the server's `staffDataChanged` areas; ticket/dispute/report case events count as `tickets` / `disputes` / `reports`). `useStaffCaseEvents` (`lib/staffCaseEvents.ts`) runs on the same bus. One set of socket handlers serves every subscriber; each subscription folds bursts into one call, never overlaps its own calls (return the reload promise), waits while the tab is hidden, re-reads after a reconnect and every 45 s while the socket is down. `StaffOutlet` connects the socket for the whole console. Live reloads must be silent: keep the shown rows, never show the first-load spinner or an error toast, and keep form state (typed reasons, picks, unsaved settings drafts, the open file in an inspector). Open modals re-read their own record (functional `setSelected` updates so a closed modal never reopens). Topics that change outside this API get a `pollMs` too: the admin dashboard (staff presence, 60 s), video projects (the editor service, 60 s) and Analytics (server-cached for 60 s, poll only). A new console view must subscribe, and a new member route that changes what a desk shows needs a `MEMBER_RULES` entry (`docs/api.md`).
- System settings re-read live, and sections with unsaved edits keep their draft and base version. When another admin saves a section being edited, a notice offers "Discard mine and load theirs"; saving anyway still meets the 409 prompt.

## Component practices

- Admin warning catalog, standing punishments, and point thresholds live under Moderation → Policy (`/admin/moderation?tab=policy`, `AdminWarningsPanel`). Legacy `/admin/warnings` redirects there. Staff warn pickers load `/api/admin/warning-catalog` (or `/api/moderator/warning-catalog`) instead of a hardcoded list. Warning duration is displayed read-only; staff cannot set it.
- Admin badge catalog lives under Settings → Badges (`/admin/system-settings?tab=badges`, `AdminBadgesPanel`). Legacy `/admin/badges` redirects there. It loads `/api/admin/badge-categories` for the category dropdown. Staff pick a live category or create one inline. Do not send a free-text category on badge save. The Grant section groups badges by category. Profile pins, the pin modal, and discovery cards hydrate catalog rows (including honorary badges) with `category` from the API.
- Admin System settings (`/admin/system-settings`, `systemSettings/`): one draft per section (Platform, Economy, Security), one sticky `SaveBar` per section, field errors from `settingsLogic.ts` (mirrors the server `rules`) merged with the server's 400 `errors`, and a confirmation listing high-impact changes (`saveRisks`) before saving. Each save sends the section's `baseVersion`; a 409 opens a reload prompt. Unsaved edits are guarded on reload and on link clicks (`useUnsavedChangesGuard`; the console router has no `useBlocker`). Number fields use `NumberInput` (text + `inputMode`, emits `NaN` while invalid) instead of `type="number"`.
- Admin sidebar lists Reports only inside Moderation → Pending cases (no duplicate Reports nav item).
- Moderation → Activity log (`ActivityLogTab`) reads `/api/admin/moderation/activity`, so its search, filters, date range, sorting and paging cover the whole history instead of the slice in the page overview. `ActivityDetailModal` re-reads one entry and shows the event, its impact, target, actor, reference, every metadata field, the reversal trail and the raw row. Shared formatting lives in `moderation/moderationFormat.ts`; do not re-add per-file date helpers there.
- Moderation → Management → Forum and the Forum Moderator desk both render `moderation/ForumModerationDesk`, which takes `apiBase` (`/api/admin/moderation/forum` or `/api/moderator/forum`) and optional `accent` / `onViewChange`. Change the desk once; both consoles follow. Forum Moderator mounts it once as **Forum Control** (`/moderator/forum/forum-control`) with Discussions | Groups tabs (`?view=groups`). Legacy `/forum-discussion` and `/groups` redirect there.
- Same shared-desk pattern for Marketplace Control and Jobs & Gigs Control: admin Management sections pass `apiBase` (`/api/admin/moderation/marketplace` or `…/jobs`) plus `embedded`; moderator pages keep the default mod API roots. Listing case review reuses `ListingDetailModal` against the admin marketplace API. Listing detail includes the linked market asset so staff can review pending assets that are not yet public on `/assets/:id`: every content file (original name, format, size, specs, processing status and error), showcase images, template metadata, tags, buyer activity, reports on the listing or asset, seller standing, copyright signals (other assets with a same-size, same-type upload or the same title) and the listing's staff history. `ListingFileInspector` switches between the watermarked preview and the original upload; originals come from `GET {apiBase}/listings/:id/media/:mediaAssetId/original` (`?download=1` for an attachment), a 15-minute signed link, because originals under `asset-originals/` are private and pending video/audio has no proxy until processing ends. Never build a CloudFront URL for an `asset-originals/` path; the detail API drops such paths.
- Marketplace listing actions live in `marketplace-moderator/listingActions.tsx` (`LISTING_ACTIONS`, `actionsForStatus`, `ListingReasonDialog`); the queue's row menu and the detail modal both use them. Approved listings can be delisted or sent back to `pending` ("Require re-approval", the copyright path); both need a reason, stored in `marketplace_listings.moderation_note` (rejections keep `rejection_reason`) and sent to the seller.
- The Marketplace Moderator console has no Restrictions tab: marketplace enforcement is issued from a report case. Its ticket desk and ticket API only serve marketplace ticket types that Admin has not taken over (escalated to Admin or handled by an Admin); sending a ticket to another desk or escalating it to Admin closes it on this desk.
- Ticket detail has a category **Case** tab (`TicketCasePanel`, every desk). The modal loads `GET {endpointBase}/:id?include=case` once and keeps `caseContext` in its own state, because update responses do not carry it; it re-reads the case after an appeal decision or a category change. Layout by `caseContext.kind`: appeal (the penalty under appeal and whether it is still active, what each decision does, earlier appeals on that penalty, the account's other penalties, standing, active punishments, standing history, area actions, past warnings, previous appeals, denial hold, Case ID lookup), marketplace (listing, files, reports, review history, the buyer's licenses, seller listings, reported seller), jobs (contract, both parties' standing, milestones, contract disputes, escrow, posting), forum (post, group, forum restrictions), billing, account, editor and safety. Member standing cards use `moderator/shared/StaffStandingSummary`; the dispute case file reuses it for both parties.
- Ticket detail "Category & routing" (`TicketDetailModalShell`, every desk): **Change category** sends `{ action: 'recategorize', type, reason? }` and stays inside the ticket's current desk (handler and status kept); **Send to another desk** and **Escalate to Admin** send `assigned_role` + `type` (+ optional `reason`). Reasons land on the ticket timeline.
- Marketplace listing ids are UUIDs. Never pass them through `Number()` (it produced `/listings/NaN` and a 500 in the admin Listing approvals modal).
- `ModeratorReportsPage` reads `?q=`, `?status=`, `?priority=`, `?assignee=` once on mount and passes them to `ReportDesk` as `preset`. Pass `listingApiBase` to let a report case open the linked listing (`ReportCaseDetailModal` shows `subject.marketplace` and `history`).
- Marketplace dashboard reads `ticketSla`, `reportSla`, `activity` (14 days), `team` and `sellersToWatch` from `/api/moderator/marketplace/overview`; alerts carry `title`, `detail`, `count` and `action: { tab, query }`.
- Admin User & Team → Restrictions embeds `ModeratorRestrictionsDesk` at `/api/admin/restrictions` (full admin capabilities). Specialist mod consoles may keep their own Restrictions routes; the Forum Moderator console does not — warn / timeout / suspend stay on User & Team.
- Admin User & Team → Team accounts lists business teams only: `/api/admin/teams-management` leaves out contract workspaces (`teams.team_type = 'contractual'`) and their stats. Pass `?include=contractual` when a look-up must find any team account (the wallet detail modal does).
- Admin Moderation → Identity & business verification lists member identity cases (`verify-<userId>`) and team business submissions still Pending or Resubmitted (`verify-business-<teamAccountId>`, `verificationKind: 'business'`). Both open `VerificationModal` through `moderation/verificationCase.ts`.
- Jobs & Gigs Moderator console has no Restrictions page (`/moderator/jobs/restrictions` redirects to User & Team); enforcement happens in a report case or User & Team → Users. Jobs & Gigs Control (`JobsGigsControl`) sorts reported postings first, shows per-posting open-report counts, and every Pause / Close / Archive goes through `PostingReasonDialog` (reason required). `jobs-moderator/PostingDetailModal` loads and moderates one posting on its own (reports on the posting, moderation history, owner history) so the dashboard and Control open the same review; shared posting helpers live in `jobs-moderator/postingUi.tsx`.
- Admin → Credits & economy and Support → Credits & Wallets (`/moderator/support/credits`) both render `creditEconomy/CreditEconomyDesk` (`variant` admin | support). Tabs: Overview | Wallets | Holds | Ledger (`?tab=`, legacy `?tab=audit` → ledger); `?wallet=<id>` opens `WalletDetailModal`; `?tx=<id>` opens `LedgerEntryModal` (one entry, its linked rows and the timeline of its contract escrow / reference / dispute, from `GET /api/admin/economy/ledger/:id`; linked rows open in place with a Back trail). Wallets, Holds and Ledger page on the server through `usePagedList` (`economyUi.tsx`). Every tab keeps its filters in the URL — Ledger: `q`, `kind`, `type`, `status` (incl. `settled`), `from`, `to`, `since` / `older` (rolling hours), `min`, `max`, `sort`, scope `walletId` + `direction`, `accountId`, `ref` + `refTable`, `dispute`, `contract` (mapping in `ledgerShared.tsx`); Wallets / Holds: `q`, `accountType`, `hold`, `balance`, `accountStatus`, `sort` (`WalletsTab.tsx`) — so any view survives reload and Back; switching tabs drops the old tab's params. Overview figures and alerts link with the exact filter the server counted with (`flow_*` kinds, `settled`, `sinceHours`), and the ledger shows the matching entry count and credit total, so the numbers agree. Alerts render on the Overview only. The ledger has one "Show" picker (`LEDGER_SHOW_OPTIONS`: a `kind` or one `type`; overview-only kinds appear under "From the overview" while applied), plain row titles (`entryTitle` / `typeLabel`), and dates and amounts under More. From / To are the viewer's calendar days (`tzOffset` is sent). Every row shows chips for its links (fee taken, fee charged on, reverses, reversed by, unpaid payout) that open the linked entry, so a fee never has to be searched for. The expanded detail offers "Show in ledger" scopes (a wallet, the whole contract, the same reference, the same dispute) that replace the filters. Five quick views sit under the filters; Export CSV writes every matching row (up to 5,000) via `fetchAllPages`. Shared row pieces (`LedgerEntryDetail`, `LedgerLinkChips`, `exportLedger`) live in `ledgerShared.tsx`. Adjust / hold / release dialogs live in `CreditActionDialogs.tsx`. Economy settings and revenue links are Admin only.
- Support Moderator console has no Restrictions page (`/moderator/support/restrictions` redirects to User & Team); enforcement happens in a report case or User & Team → Users. Its Ticket Management shows only the support queue, so it hides the Queue filter and keeps Support group + Type (`?subgroup=` deep-links work). Its Reports page passes `scopeOptions` to `ModeratorReportsPage`: Support scope (default, no query param) or All platform (`?scope=all`).
- `ModeratorTicketDesk` has Queue and My tickets views (`?view=mine`), matching the Support desk. "Mine" matches on the signed-in staff id, and the summary cards plus quick chips describe the selected view.
- Admin Analytics (`/admin/analytics`, `analytics/`): tabs Overview | Members | Community | Revenue & credits (`money`) | Operations | Traffic & rate limits | Feedback. Old `?tab=growth|economy|finance|health` map to the new tabs. The date range lives in the URL (`?range=`, `?from=&to=` for custom, `?bucket=`); the default 30 days sends no params so it matches the route prefetch. Switching ranges keeps the previous range on screen, dimmed, until the new one arrives; Refresh sends `refresh=1`. Every tab reads the one overview response; the Revenue & credits records (`FinanceLedger`, `?ledger=topups|invoices|subscriptions|cashouts`) page, search and export CSV on the server. Credit-ledger browsing stays on the Credits & Economy desk. Formatting helpers and the per-metric colors live in `analyticsFormat.ts`, shared tiles and panels in `analyticsUi.tsx`. The shared charts in `AnalyticsCharts.tsx` (also used by Tickets and the moderator dashboards) take optional `formatValue` / `tooltipLabels`, skip `null` points, and use solid fills.
- Platform Feedback lives under Analytics → Feedback (`/admin/analytics?tab=feedback`). Legacy `/admin/feedbacks` redirects there.
- API traffic and 429 monitoring lives under Analytics → Traffic & rate limits (`/admin/analytics?tab=traffic`, `analytics/components/RateLimitMonitorPanel`). Like Feedback, it is a standalone tab (`STANDALONE_TABS`) that loads its own data, not the analytics overview. It polls `/api/admin/rate-limits` every 10 seconds while the page is visible and auto-refresh is on.
- Staff ban, suspend, and timeout pickers load `/api/admin/punishment-catalog` (or `/api/moderator/punishment-catalog`). The catalog duration is the default. Staff may override it and must still write a reason.
- Cases (`/support/cases`, `pages/user/support/CasesPage.tsx`) and the appeal page (`/account/appeal`, `pages/user/account/AccountAccessPage.tsx`) show the same tickets and disputes through `appeal/CaseInbox` and `appeal/useCaseLists`. Tickets and disputes are not in the chat inbox: the chat store refuses case conversations (`memberCaseTarget`) and `components/cases/CaseConversationRedirect` sends old inbox links to Cases (`?ticket=` / `?dispute=` / `?conversation=`). Every reply box, read-only reason, rating, "waiting for you" flag and public-page link comes from the server's per-case `access` (`lib/cases.ts` types, `backend/services/CaseServices.js` rules), so banned, locked, suspended and active members always see what the write paths accept; views re-read it on `caseUpdated`, `disputeUpdated`, `ticketStateChanged`, case notifications, reconnects and standing changes (a 60-second poll is only a fallback). The site-wide case bar (`components/cases/CaseStatusBar`, stacked under the standing bar in `AccountRestrictionHost`) and the sidebar **Cases** badge read `useCaseStore` (`GET /api/users/cases/summary`). The appeal page composes `appeal/PenaltyAppealList` (every active penalty from `GET /api/users/appeals` via `appeal/useAppealOptions`, each with Appeal this / Open appeal / its decision), `appeal/AppealForm` (one penalty; sends `appealTarget`) and `appeal/CaseInbox`. With a single appealable penalty the form opens directly. Per-target copy (`APPEAL_TARGET_COPY`, keyed by appeal target type) and length limits live in `appeal/appealShared.ts` (limits mirror `appealLengthError` in `AdminTicketsControllers.js`). Appeal decisions render as `appeal/AppealDecisionCard` in both the member thread and the staff ticket chat (`dark` there), like `DisputeDecisionCard`. Staff decide through `ticketManagement/AppealDecisionDialog` (lift within 24h / now / earlier date; on deny, optional suspend or ban from the punishment catalog; note to the member). The generic ticket page sends "Appeal an account penalty" to `/account/appeal`. The appeal form, ticket replies and dispute replies take up to 4 images, PDFs or videos through `appeal/appealAttachments.tsx` (tickets upload to `ticket-attachments`, disputes to `chat-attachments`). `/contracts/disputes` keeps progress, rulings and payouts; its conversation links go to Cases. Replies send optimistically: the bubble shows at once ("Uploading…" / "Sending…"), files are handed over with `usePendingFiles().take()`, and a failed send stays with Retry / Remove; the composer never waits. A selected case is laid out like the public dispute page (`appeal/caseView.tsx`, reusing `publicDisputeParts`: `PartyTile`, `CaseProgress`, `ThreadMessage`, `DayDivider`, `Panel`): a header card (number, type, public/private and stage chips, title, filed/updated/replies, disputer vs disputee or member vs support), the discussion with All / Rulings / Parties & staff filters (disputes) and day dividers, and a side column (progress, your part, payout, case or ticket details, complaint or what was reported with the form answers, activity, tips). The side column sits beside the thread on `2xl` screens and folds into **Case info** below that (open by default on Cases, folded on the appeal page). Dispute `details` come from the party read (`loadDisputeCaseDetails`, with party avatars). `MentionText` links plain `@handles` by pattern and also any handle in the `mentions` map by exact text, because older generated handles hold spaces and commas.
- User-facing screens say **Platform Merit**, never “warning points.” Merit is `100 − active warning points` from standing (`frontend/src/lib/merit.ts`). Staff desks keep warning-point language.
- Follow the existing dark Ensemble theme, spacing, typography, borders, and controls.
- Do not introduce gradients or visually unrelated component systems unless requested.
- Reuse existing components and tokens before creating new ones.
- Keep page components focused; move reusable or complex behavior into components/hooks.
- Preserve responsive behavior and keyboard navigation.

## Forms

- Display field-level errors near the corresponding input.
- Required fields need both frontend guidance and backend validation.
- Disable duplicate submissions while a request is pending.
- Never treat frontend validation as a security boundary.
- Password guidance stays hidden while empty; while typing, unmet rules use a neutral white dash and met rules use a green check.

## Realtime UI

- Subscribe once and clean up listeners on unmount.
- Avoid registering duplicate handlers on rerenders.
- Merge events by stable ID and treat duplicates as normal.
- Fetch authoritative state on initial load/reconnect.
- Presence should use heartbeat/connection state with a timeout, not a permanent boolean.

## Editor export and comment feedback

- The editor upload storage bar uses `red-500` at 80% usage and above, and the normal primary color below 80%. Its width and warning threshold both use actual used bytes divided by the database plan allowance.

- The export modal displays a minimum of 1% after one second of an active export. This is a presentation-only floor; server progress is unchanged. Queue position, failures, completion and cancellation retain their existing states.
- Completed exports auto-request a download once after three seconds and keep the Download button available for manual retries. A browser download request is not treated as confirmed saved. Closing the completed-output modal calls the existing render cleanup endpoint and resets export state; output stays available until that dismissal, subject to existing expiration. Closing an active render only hides its progress modal.
- The active project/scene comments WebSocket invalidates the authenticated comment list. Each successful snapshot is compared by entry ID to detect mentions and replies to the viewer's top-level comments; the server's author-only `canDelete` flag excludes self-notifications. Older overlapping responses are ignored.
- Navbar counts and entry/thread badges track unread entries. Notifications clear for a thread only when its floating thread panel opens, including replies received while that thread remains open. Viewing the main comments list never acknowledges notifications. Incoming entries show a five-second automatic tooltip and play the main site's `notification.mp3`, subject to browser autoplay permission.
- Notification checkpoints contain known, unread and acknowledged entry IDs, keyed by user and project/scene in browser localStorage, with an in-memory fallback. They persist until browser storage is cleared; deleted entries are removed from unread counts on refresh, while known/acknowledged IDs remain to prevent repeat alerts after incomplete snapshots. Opening a floating thread acknowledges its individual entries, so reading two replies and later receiving a third contributes only one unread notification. First visits baseline existing comments without announcing them; subsequent snapshots (including reconnect/reload) detect new IDs. Read state is browser-local, not synchronized across devices. No database migration or additional WebSocket is used.
